# 开发 skill 现在规定了客户端实现标准

- **Date:** 2026-08-16
- **Type:** process
- **Scope:** `skills`
- **PR:** [#170](https://github.com/Prism-Shadow/agenthub/pull/170)

[English](2026-08-16-client-implementation-standard.md)

## 变更内容

- **回放要最小化，而不是穷尽。** `fidelity` 是一条例外通道：只有当实况探测证明缺了它请求就会失败、或模型表现会退化时，某个字段才配写进去。API 会重新生成或直接忽略的、由服务端产生的 id —— reasoning item id、output-item id —— 一律不存；而 `phase`、thinking signature、以及严格上游所要求的确切 reasoning 字段名，则要存。`fidelity` 绝不能重复通用字段已经承载的内容。
- **`tool_call_id` 是强制的**：必须抓取并回放服务端的 call id。当某种格式同时带有 item id 和 call id 时，把结果与调用关联起来的是 call id。
- **Stage 2 新增了做出该判断所依据的探测。** 抓取完成后，把 assistant 轮次反复重发，每次移除一个候选字段，并把 API 能容忍的移除项记录在抓取旁边。
- **每个协议家族指定一个参考客户端。** Responses 风格协议以 `gpt5_5/` 为准，Chat Completions 以 `openai/` 为准 —— 方法顺序、控制流、命名都保持一致，使新客户端读起来就像是对参考实现的一个 diff。
- **由可读性决定代码放在哪里。** 默认内联；辅助函数只用于确实很大、自成一体、内联会淹没主流程的代码块，绝不用于几行代码，也绝不在参考客户端自有的私有方法旁边另起一层。
- **只按 delta 处理流式输出。** 部分工具调用在 item-added 事件上开启，通过参数 delta 累积，并在终止事件处作为完整的 `tool_call` 发出。完成类事件只被忽略而不做交叉校验，服务端错误事件（`response.failed`、`response.error`）交给未知事件兜底。

## 问题

[MiniMax M3 客户端](2026-08-03-minimax-m3.zh.md)交付的第一版被评审拆掉了一大半：往 `fidelity` 里存了 API 根本不需要回传的字段、包了一层围绕 dict/SDK 双路访问的模块级辅助函数、对完成的 item 做 JSON 校验、翻译服务端错误事件、以及从完成事件而不是 delta 来定型工具调用。这些都不是粗心 —— 每一处都是照着当时写着的 skill 做的。

正因如此，才值得从源头修。skill 的 Stage 3 要求转换必须"双射……完全复现原始内容，包括 `fidelity` 载荷"，这读起来就是"把每个字段都存下来"的指令；而且它没有指定任何参考实现，于是新客户端长什么样，完全取决于谁来写。skill 是成因，而不是旁观者。

## 决策

Stage 3 把标准写成作者可以遵循、评审可以核查的规则：什么才配进 `fidelity`（只有探测证明必需的）、哪个 id 是强制的（`call_id`）、新客户端照着哪个文件的形态写（`gpt5_5/` 或 `openai/`）、代码放在哪里（默认内联，辅助函数只用于大段自包含逻辑）、以及流式处理读什么（只读 delta，绝不读完成类事件，绝不翻译服务端错误事件）。提供依据的探测归 Stage 2 负责，因为最小集合是测出来的，而不是推理出来的。

"双射……完全复现原始内容"那条规则是被删除而不是被补充说明：把它留在新规则旁边，等于把制造了这些缺陷的矛盾一并留下。

## 备选方案权衡

- **在原有措辞旁边新增规则。** 否决：旧规则会主动把人推向"什么都存"，从头读下来的作者会撞上矛盾，并且满足其中任意一半都说得通。
- **用 linter 而非文字来约束形态。** 否决："除非代码块很大否则不要辅助函数层"、"读起来像对 `gpt5_5` 的 diff"、"只存 API 需要回传的东西"，这些都是 linter 做不了的判断。其中真正可机械化的部分 —— 探测 —— 是一个工作流步骤，而不是静态检查。
- **交给代码评审。** 否决：评审确实抓到了这些缺陷，但代价是把一个已交付的 PR 整体重写。skill 才是 agent 在动手写的时候读的东西，标准就该放在那里；评审仍然作为兜底。
- **从抓取推断最小回放集合，而不做探测。** 否决：抓取显示的是 API *发出*什么，而不是它*需要回传*什么。只有逐项移除的探测才能把两者区分开。

## 验证

- 每一条规则都能追溯到 [#167](https://github.com/Prism-Shadow/agenthub/pull/167) 中被移除的一个具体缺陷，以及它现在所指向的参考客户端的形态。
- 探测流程不是纸上谈兵：针对 MiniMax M3 的四个请求证明了 reasoning item 仅凭其文本即可回放、完全不需要 id，而且这种无 id 的回放照样命中提示缓存（512 个 cached token）。修订后的客户端在两种语言下都通过了该模型范围内的全部 e2e。

## 风险

- 这些规则把形态钉在了今天的参考客户端上。如果 `gpt5_5/` 或 `openai/` 被重构，"读起来像对参考实现的 diff"的含义就会悄悄改变，本条目的 `## 决策` 也必须随之重新审视。
- "确实很大、自成一体的代码块"是一个判断，而不是阈值。刻意不给行数标准 —— 数字规则会被钻空子 —— 但两位作者仍可能有分歧，最终由评审来定。
