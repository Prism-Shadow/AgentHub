# 结构化的双语更新日志条目，以及两条开发 skill 规则

- **Date:** 2026-08-16
- **Type:** process
- **Scope:** `changelog`, `skills`
- **PR:** [#170](https://github.com/Prism-Shadow/agenthub/pull/170)

[English](2026-08-16-changelog-format-and-skill-rules.md)

## 变更内容

- 每个详情文件都以一个元数据块开头 —— `Date`、`Type`、`Scope`、`PR`、`Issue`、`Breaking` —— 紧接标题之下，并保持这一固定顺序。全部 29 个条目都带上了它，每个发布版本 README 中的行也在详情链接旁附带了 PR 链接。
- 裸写的 `(#N)` 引用改成了真正的链接。裸写的 `#N` 在 Markdown 文件里会渲染成纯文本（GitHub 只在 issue 与 PR 评论中为其自动生成链接），因此这些引用当不了链接用。
- 未发布的内容被钉在 `changelog/unreleased/`：该目录以状态命名而非版本号，因为版本号要到发布时才确定。
- 正文有了经过设计的形态：没有任何决策的变更用简式，其余用完整式（`## 变更内容`、`## 问题`、`## 决策`、`## 备选方案权衡`、`## 验证`、`## 风险`、`## 兼容性`、`## 待办`），顺序固定、词汇固定。
- 每个文件都有两种语言 —— `<name>.md` 与 `<name>.zh.md`，逐节互相对应：29 个详情条目、8 个发布版本 README、根目录 `CHANGELOG.md`，以及约定文档本身。
- `agenthub-dev` skill 新增了两条规则。Stage 2：当抓取到的交互中有部分内容无法序列化为 JSON 时，保存其 `str()` 形式并用一个 JSON 对象包裹，使 `.jsonl` 仍可解析，而不是丢弃该事件或手工改写它。Stage 4：`AVAILABLE_MODELS` 条目是新模型唯一有权做出的测试改动；共享的 e2e 测试套件是每个客户端本就必须满足的契约。

## 问题

这些条目本来就装着正确的信息，只是形态不对。PR 归属即便存在也埋在正文里，而正文之上没有任何内容说明该条目属于哪类变更、触及了哪些模块，于是一个 agent 要回答"`temperature` 是从什么时候起不再被接受的，由哪个 PR 完成？"，就必须把条目从头读到尾。正文也已经漂移：同一个意思出现了四种小节名 —— `## Protocol findings`、`## Protocol implementation`、`## Implementation`、`## Implementation notes` —— 而且根本没有地方安放一次变更背后的证据，以及它带着哪些风险交付。此外整棵树只有英文，而本仓库的评审是用中文进行的。

## 决策

三处固定，一处灵活。元数据块固定且可机械校验。正文词汇固定：一组有文档记载的小节名，顺序固定，并为没有做出任何决策的条目保留简式。双语配对固定：缺少对应版本的文件就是没写完。保持灵活的是散文篇幅和专门小节 —— 一次变更真正的细节正该落在那里。

元数据块在两种语言里都保持英文 —— 字段名、`Type` 取值、`Scope` 标识符、日期、链接 —— 这样一条 `grep` 就能在整棵树上回答问题，与语言无关。只有散文、小节标题和 `Breaking` 的理由被翻译，而标准小节标题有固定译法，因此在中文侧同样可 grep。

## 备选方案权衡

- **朴素的 `Key: value` 行**，即启发了本方案的 [deepseek-harness agent notes](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/README.md) 所采用的形式。否决：连续的行在渲染时会挤成一个连排的段落。项目符号列表能正确渲染、仍可按字段名 grep，且原始文本形态下读起来一样。
- **YAML frontmatter。** 否决：不同查看器的渲染结果不一致，而且这些字段值得在正文里被读到，而不是藏在正文之上。
- **另建一个索引文件**，把条目映射到 PR、类型与范围。否决：索引会与被索引对象逐渐脱节。把字段放在散文旁边才能保持为真。
- **把元数据块也翻译掉。** 否决：那会把每条查询一分为二，`grep -rl 'Breaking:' changelog/` 只能返回一半答案。
- **把完整正文结构回溯套用到历史条目上。** 否决：27 个既有条目里有 21 个是标题加一个项目符号列表。把它们的正文改写成固定的小节方案，只会无谓地扰动历史记录；它们只加了一个 `## What changed` 标题，此外没有任何改动。

## 验证

- 一个格式校验器校验整棵树：字段顺序、`Date` 与文件名一致、`Type` 落在封闭集合内、每个 `PR`/`Issue` 取值都是完整链接、任何地方都没有裸写的 `#N`、带 `Breaking` 的条目都配有 `## Compatibility`、所有相对链接与 `[details]` 链接都可达、`changelog/unreleased/` 存在且没有带版本号的目录自称未发布，以及每一对文件在小节数、元数据字段、互链上都对得上。它在 8 个发布版本、29 个条目、39 对文件上通过。
- 这个校验器两次证明了自己的价值：它抓到了一个标了 `Breaking: yes` 却没有 `## Compatibility` 小节的条目；而它自己的第一版把正文里以粗体开头的要点误当成元数据，报出三个假阳性 —— 正因如此它现在会在第一个空行处停止解析。

## 风险

- 校验器位于仓库之外，因此没有任何机制能阻止一个无视该约定的 PR。把它接进 CI 是显而易见的下一步，本次变更刻意没有包含它。
- 词汇表只约束标准小节。专门小节的名字仍可能像以前那样漂移，而只有评审会注意到。
- 翻译质量无法机械校验。结构、元数据和链接是机械验证过的；中文是否说出了英文所说的内容，则没有。

## 待办

- 把格式校验器接进 CI，使格式不合或缺少配对的条目直接让构建失败，而不是等评审发现。
